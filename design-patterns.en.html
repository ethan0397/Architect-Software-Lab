What is a design pattern?

A design pattern is a general, optimized solution to a recurring software design problem in object-oriented programming (OOP). It is not a rigid template — it is a way to organize code so coupling drops, tests get easier, change becomes safer, and teams communicate faster.

OOP

A technique, not a language

Patterns work in Java, C#, TypeScript, Python, and more — as long as you understand classes, interfaces, inheritance, and polymorphism.

Prerequisite

Learn OOP first

If you are still new to programming and OOP feels shaky, build that foundation first. Patterns pay off once object thinking is natural.

Key point Patterns are not the goal. The goal is solving a design problem — patterns are just tools. Further reading: Design Patterns overview — Viblo

Why learn design patterns

1

Faster development

Reach for proven tools for common design problems instead of reinventing each time.

2

Shared team vocabulary

Saying "Facade" or "Observer" lets everyone picture the structure without long explanations.

3

Reusable solutions

Apply community-tested approaches to problems that show up again and again.

4

Easier maintenance

Avoid design choices that break later; codebases become easier to extend and upgrade.

23 Gang of Four (GoF) patterns

The classic set from Design Patterns: Elements of Reusable Object-Oriented Software splits into three groups by purpose. Click any pattern for a detailed article.

1. Creational patterns

The Creational group has 5 patterns:

  • Singleton
  • Factory Method
  • Abstract Factory
  • Builder
  • Prototype

These patterns hide object creation logic instead of scattering new everywhere, so the program stays flexible about which object to create in each situation.

2. Structural patterns

The Structural group has 7 patterns:

  • Adapter
  • Bridge
  • Composite
  • Decorator
  • Facade
  • Flyweight
  • Proxy

These patterns define relationships between classes and objects. They matter more as systems grow — class diagrams are a good way to track them.

3. Behavioral patterns

The Behavioral group has 11 patterns:

  • Interpreter
  • Template Method
  • Chain of Responsibility
  • Command
  • Iterator
  • Mediator
  • Memento
  • Observer
  • State
  • Strategy
  • Visitor

These patterns coordinate behavior between objects — collaboration and sequence diagrams help you follow them.

Fast rule Do not ask whether a pattern is “good.” Ask what design problem you actually have, and then see whether a pattern makes the system simpler.

Creational patterns

Factory Method

Centralize object creation

Use it when implementation choice depends on config, environment, or input.
Abstract Factory

Create related object families

When you need a coordinated set of UI or provider implementations.
Builder

Create complex objects step by step

Helpful when objects have many optional fields or a multi-step construction flow.
Prototype

Clone existing objects

When construction is expensive; clone a template and tweak it.
Singleton

One shared instance

Useful for root configuration or logging, but easy to abuse into global state.

Structural patterns

Adapter

Integrate vendors safely

Normalize external interfaces so internal domain logic stays clean.
Bridge

Separate abstraction from implementation

Swap implementations without affecting clients.
Composite

Part-whole trees

Menus, folder trees, org charts — treat leaves and groups uniformly.
Decorator

Add logging, cache, or retry

Wrap behavior without modifying the original class.
Facade

Hide multi-step flows

Turn a large use case into one clear entry point.
Flyweight

Share common state

Save memory when thousands of similar objects exist (icons, glyphs).
Proxy

Control access

Useful for lazy loading, access control, or remote proxy scenarios.
Repository

Protect the domain from ORM details

Create a boundary between business logic and persistence concerns.

Behavioral patterns

Strategy

Multiple behavior variants

Turn long if/else branches into separate interchangeable strategies.
Observer

One event, many reactions

A publisher emits an event and subscribers handle their own responsibilities.
Command

Package actions as objects

Very useful for queues, retries, undo/redo, and deferred execution.
State

Behavior by lifecycle state

Great for order, booking, or payment state transitions.
Template Method

Fixed algorithm skeleton

Useful for import pipelines or workflows with the same structural steps.
Chain of Responsibility

Sequential processing stages

Fits middleware, validation chains, and approval flows.
Iterator

Traverse collections

Hide internal structure while clients loop over elements.
Mediator

Centralize communication

Chat rooms, dialog coordinators — objects stop calling each other directly.
Memento

Save and restore state

Undo in editors, snapshots before big changes.
Visitor

Operations on a structure

Add new operations across many element classes without editing them.
Interpreter

Small grammars

Parse expressions or simple rule engines.

Quick selection guide

If you notice...

  • Many if/else branches by behavior variant -> Strategy
  • Object creation logic scattered everywhere -> Factory Method
  • An object with too many constructor parameters -> Builder
  • Vendor APIs polluting your domain -> Adapter
  • A use case that calls 5-7 internal services -> Facade

Or if you notice...

  • You want cache, logging, or retry -> Decorator
  • An object changes behavior by lifecycle stage -> State
  • A request passes through many stages -> Chain of Responsibility
  • An action needs queueing or undo -> Command
  • Business logic is glued to ORM or SQL -> Repository
